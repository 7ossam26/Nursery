# Phase 05 licensing, slots, and nursery settings

## Runtime contract

Migration `0003_licensing_settings.sql` adds seven capabilities (`licensing.manage`, `seats.release`, `branding.manage` reserved; `modules.manage`, `users.manage_staff`, `users.create_parent`, `parents.block` delegable), `license_limits` (unconfigured until Superadmin first saves it), `seat_reservations` (append-only per account, at most one active row per account, partial unique index on `account_id where released_at is null`), `license_renewal_payments`, append-only `licensing_audit_events`, `nursery_settings` (seeded with the shipped default theme so branding always has a value), `module_settings` (five fixed rows: FINANCE, ATTENDANCE, EXAMS, HOMEWORK, HEALTH; no branch column, so every branch reads the same values by construction), and `module_settings_history`.

`LicensingService` (`apps/api/src/modules/licensing/service.ts`) mirrors `OrganizationService`'s `withPolicy` pattern but with its own advisory lock (`7190501`, distinct from organization's `7190401`) so licensing-settings edits and organization-policy edits never contend. Seat allocation does not use that lock at all: `reserveSeat` takes `select ... from license_limits where singleton for update` inside the caller's own transaction, counts active `seat_reservations` for the kind, and inserts a reservation only if under capacity — this is the literal row lock the acceptance fixture (A04) exercises, not a coarse subsystem-wide serialization.

`organization/policy.ts`'s `loadPolicy` now also computes `licenseStatus` (`NOT_CONFIGURED | ACTIVE | GRACE | SUSPENDED`) from `license_limits` in the same statement that builds capabilities/scope, using `subscriptionAccessStatus` (`packages/domain`) against the Cairo business date from `cairoIsoDate()`. It throws `LICENSE_SUSPENDED` for every non-SYSTEM kind when suspended; SYSTEM never gets blocked (root support access). Because `AuthService.project` calls `loadPolicy` for every authenticated request (including inside `login`), a suspended installation blocks new logins for staff/guardians too, not just already-open sessions. `licenseStatus` also rides along on `CurrentAccount` so the web app can show a GRACE warning without a second call.

`AuthService` gained two small public primitives reused by licensing: `changeStatusInTransaction(tx, actorId, targetId, input)` (the actual status/history/revoke/audit work, factored out of the existing SYSTEM-only `changeStatus` route so both paths share one implementation) and `setTemporaryCredential(tx, targetId)` (issues a fresh one-time password, used by account restoration). Neither changes the existing SYSTEM-only `/api/v1/auth/accounts/:id/reset-password` route or its tests.

### Seats: reservation, release, restoration

`provisionStaff`/`provisionParent` create the account row and its seat reservation in one transaction (`users.manage_staff` / `users.create_parent`); a capacity miss or an unconfigured license rolls the whole transaction back, so there is never an orphan account. `releaseSeat` (`seats.release`, SYSTEM-only reserved capability) is the only action that ends an active reservation; it also sets `accounts.status = 'RELEASED'` and revokes sessions, but never deletes child/financial/audit history. `restoreAccount` (also `seats.release`) is the only way back from `RELEASED`: it re-runs `reserveSeat` against current capacity, sets status back to `ACTIVE`, and issues a fresh one-time credential — the account's old password is never revived. `deactivateAccount`/`reactivateAccount` (staff, `users.manage_staff`) and `blockAccount`/`unblockAccount` (parents, `parents.block`) never touch `seat_reservations`; they explicitly reject a `RELEASED` target with `licensing.useRestoreAction` so a delegated admin without `seats.release` cannot silently reinstate an account without a real reservation (an account that bypassed this would log in successfully while occupying an uncounted slot — this was caught and fixed during this phase's own testing, not shipped).

### Subscription, estimate, and renewal

`saveLimits` (`licensing.manage`) is an upsert: the first save has `expectedVersion: null`; later saves must match the current version and are rejected if the new parent/employee capacity would fall below currently active reservations (`licensing.belowReserved`) until seats are explicitly released. `estimatePeriodTotalPiastres` (pure, `packages/contracts`) always multiplies purchased capacities by their unit prices, or returns the agreed override when present — it never looks at how many accounts are actually active (D28). `recordRenewalPayment` inserts into `license_renewal_payments` only; no table resembling a treasury or child-fee ledger exists yet, so this cannot post business cash by construction, and a test asserts no such table exists in the schema.

### Module settings and the finance catch-up preview

`module_settings` has exactly the five rows above; there is no branch dimension to disagree across branches. `modules.manage` (delegable) gates both read and write; `organization.read` also grants read, since a role that manages one module family shouldn't need an unrelated capability just to see current state. Toggling FINANCE off never requires acknowledgement. Toggling FINANCE **on** after it was off requires calling `POST /modules/FINANCE/preview` first and then saving with `catchupAcknowledged: true`; today's preview always reports zero missing periods because no billing-generation engine exists before Phase 14 — this is a documented, honest stub for that phase's catch-up adapter, not a fabricated result. ATTENDANCE/EXAMS/HOMEWORK/HEALTH toggle freely with an impact list but no acknowledgement gate, matching D14–D15/D26 (existing history and the staff emergency panel are unaffected by a disable).

### Branding and contrast

`nursery_settings` stores name/logo path/contact fields and an 11-token theme (`packages/contracts/src/licensing.ts`, matching the tokens in [UX_AND_BRANDING.md](UX_AND_BRANDING.md)), gated by the reserved `branding.manage` capability (SYSTEM only, per the settings-ownership table — no admin capability exists to delegate this). `validateThemeContrast` (contracts, built on `contrastRatio`/`bestForeground`/`MINIMUM_TEXT_CONTRAST` in `packages/domain`) checks text-bearing pairs against 4.5:1 and is run both server-side (blocking `saveNurserySettings` with the failing pairs and their computed ratios in `publicMessage`) and client-side (the theme editor shows the same failures live before submit). The default theme is exactly the palette already hardcoded in `apps/web/src/styles.css`, so installing this migration changes nothing visually until Superadmin edits it. `GET /api/v1/licensing/branding` is public (no session required) and is the one API surface a not-yet-signed-in page may call; the web app's `BrandingProvider` applies the returned theme onto the existing CSS custom properties and sets `document.title`/the shell header name.

`BrandingProvider` deliberately uses its **own** `AuthClient` instance rather than sharing the authenticated app's client. During this phase's own e2e verification, sharing one client instance between `BrandingProvider` and the rest of the authenticated app caused an intermittent hang in heavier interaction tests (the exact underlying mechanism was not conclusively identified — narrowed to concurrent use of one `AuthClient`/transport instance rather than anything server-side, since disabling the licensing routes entirely did not fix it, while giving `BrandingProvider` an independent client did). Keeping it independent is also the more defensible design: a public, unauthenticated fetch has no reason to share session/CSRF state with the authenticated client.

## API

All routes are under `/api/v1/licensing` and reuse global authentication/CSRF/no-store headers, except `GET /branding` which is `{config:{public:true}}`.

- `GET /branding`: public `{name, logoPath, theme}`; returns the shipped default when nothing is configured.
- `GET /context` (`licensing.manage`): limits, status, purchased-capacity estimate, live parent/employee reserved counts, recent renewal payments.
- `PUT /limits` (`licensing.manage`): `{ expectedVersion: number|null, value }`.
- `POST /renewal-payments` (`licensing.manage`): manual payment ledger entry.
- `GET /modules` (`organization.read` or `modules.manage`); `POST /modules/:key/preview` and `PUT /modules/:key` (`modules.manage`): `{ expectedVersion, enabled, reason, catchupAcknowledged? }`.
- `GET /settings`, `PUT /settings` (`branding.manage`): `{ expectedVersion, value }`.
- `POST /staff`, `POST /parents` (`users.manage_staff` / `users.create_parent`): `{ username }` → `{ id, username, temporaryPassword }`.
- `POST /accounts/:id/release`, `/restore` (`seats.release`); `/deactivate`, `/reactivate` (`users.manage_staff`); `/block`, `/unblock` (`parents.block`): all take `{ reason, ... }`.
- `POST /support-context` (`support.access`, reused from Phase 04): audited Superadmin summary (status, module state, branding, staff/parent counts).

## Limitations and future-module adapters

- Finance catch-up preview always returns zero missing periods; it is a stub honestly reflecting that no billing-generation engine exists before Phase 14. When that phase lands, `moduleChangeImpacts`'s `missingPeriods` computation is the integration point to replace.
- Logo images are stored only as a path string; no upload/serving mechanism exists yet (private file storage is a later phase per D20).
- `restoreAccount` reactivates the same account identity (same username/audit trail) rather than requiring a brand-new account; this reading of "restoring an account needs a new available reservation" was chosen because the alternative (treating release as permanent and requiring a new identity) has no textual support and would make the explicit release/restore pair pointless in Superadmin's own account-recovery workflow.
- Remote management of other installations and backup/restore execution tools remain Phase 23, per this phase's stated boundary.
