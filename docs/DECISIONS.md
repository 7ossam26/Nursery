## Change procedure

### 2026-09-14 — Phase 10 exams, grades, and correction defaults (D36)

R07/U12, D14–D18: exam definitions and results reuse `learning.read`/`learning.publish` and the Phase 08 single-transaction adapter (`ChildService.withPolicy` + `LearningService.operation`/`appendInTransaction`) instead of a parallel authorization or publication path, exactly as attendance did. A classroom result-entry roster is the same date-effective, currently authorized, ≤100-active-child page as attendance/learning. Subjects and exam types are simple editable/retirable catalogs gated by a new delegable `exams.catalog` capability; every exam snapshots the subject/type name it used at creation so a later catalog rename never rewrites a historical exam's display. Exam definitions themselves (name/subject/type/classroom/date/grade format/maximum/labels) are append-only once created — no edit endpoint exists in this phase, matching the boundary against destructive editing.

Numeric results store exact two-decimal marks (PostgreSQL `numeric`, never floating point), reject any value outside `[0, maximumMarks]`, and reject non-integer marks unless the exam explicitly allows decimals; label results must be one of the exam's own snapshotted label options. A missing result is distinct from a zero score at every layer (roster, history, and the underlying learning event). `CHILD_ABSENT` is an explicit per-exam outcome, separate from the classroom-wide `NO_EXAM` bulk action, which — like attendance's no-class action — is refused once any exam already exists for that classroom/date.

Because several exams can be scheduled for one classroom/date, all of a child's exam activity that day shares one EXAM checkpoint slot/revision chain (one aggregate pending/resolved/N-A status), while each individual exam's own outcome/score/label/comment lives in adapter-owned `exam_results`, keyed by its own event. The aggregate status is recomputed on every result write: pending while any applicable exam lacks an outcome, N/A only if every applicable exam resolved child-absent, otherwise resolved. Creating a new exam for a classroom/date that already looked resolved reopens every affected child's slot back to pending via an appended transition over the existing roster page. This required a narrow, deliberate extension to the Phase 08 adapter contract — `appendInTransaction` accepts `{ aggregateTransition: true }`, usable only for `kind==='EXAM'` — letting a transition land on an unchanged status (the multi-exam "still pending" case) without touching the public custom-checkpoint transition rule (changed status, unchanged note) that STATUS_NOTE and every other kind still enforce. Migration `0008_exams.sql`; API `/api/v1/exams`; schema, routes, and evidence in [EXAMS.md](EXAMS.md).

### 2026-09-14 — Phase 09 attendance and calendar defaults (D35)

R06–R07, D06–D07, D14–D17: attendance reuses `learning.read`/`learning.publish` and the Phase 08 single-transaction adapter instead of introducing parallel authorization or publication paths. A classroom roster is a date-effective, currently authorized page of at most 100 active children. Missing remains explicit; bulk-present is a user action that selects only the reviewed unpublished page. PRESENT and ABSENT resolve the attendance slot. NO_CLASS is a new immutable snapshotted status with NOT_APPLICABLE meaning, introduced by migration 0007 in a configuration version effective no earlier than the next Cairo date. The explicit no-class action applies only to a wholly unpublished reviewed page; larger rosters use further pages under the existing D34 boundary.

Guardian planned absence is an advisory current/future inclusive range, bounded to 366 days and normalized to one mutable row per guardian/child/date. Identical submissions do not duplicate rows; a changed reason updates only dates without confirmed attendance and is audited. It never publishes attendance. An actual ABSENT event without a planned notice stages one append-only unexpected-absence alert for that effective event. Phase 12 owns delivery and recipient revalidation. Detailed attendance, learning event, audit, operation result, scoped outbox, and alert staging commit atomically. No arrival/departure field exists. See [ATTENDANCE.md](ATTENDANCE.md).

### 2026-09-14 — Phase 08 checkpoint and publication defaults (D34)

R06/U09/U10/U13, D14–D18: configuration is a whole immutable numbered set, effective the next Cairo date. All saved definition/status IDs are permanent; retire with enabled=false, and create a new ID to change semantic meaning. Each definition retains an enabled pending status; built-in outcome mappings remain available and cannot be repurposed. Optional enabled dates are inclusive. Several saves on one date retain every version; new reports select the highest version effective on their date. Lazy historical snapshots use retained date-effective placement and lifecycle records. No server draft store is introduced; forms hold input in memory until explicit publication.

Custom checkpoints gain a nursery-wide CUSTOM_CHECKPOINTS module switch, enabled on migration, because the existing ATTENDANCE/EXAMS/HOMEWORK switches do not cover custom data and A31 requires immediate disable behavior. Ordinary staff/guardian daily responses filter all disabled modules, even on historical dates; explicit currently scoped staff history keeps the retained chain available. Add reserved learning.configure and delegable learning.read/learning.publish capabilities; do not grant them silently to existing roles.

Public custom transitions append a changed status with the prior note unchanged. Changing published content requires a reasoned correction. Empty notes normalize to null. Actor-scoped operation IDs replay the original result only after fresh scope/module authorization; conflicting reuse and stale revisions are distinct errors. Classroom initial publication accepts up to 100 explicitly reviewed entries with individual exceptions; larger rosters use successive pages. Publication, audit, operation result and the scoped append-only outbox are atomic. Phase 12 owns dispatch/acknowledgments and must revalidate recipients. Migration 0006_learning.sql, API /api/v1/learning; schema, adapter protocol, tests and limitations in [CHECKPOINT_ENGINE.md](CHECKPOINT_ENGINE.md). No later-phase specialized payload or generic form builder is included.

### 2026-09-13 — Phase 05 licensing, module-dependency, and branding defaults (D31)

R01–R05/U04/U05/U07: seat reservation is a single active `seat_reservations` row per account (append-only ledger, partial unique index on `released_at is null`), allocated by locking `license_limits` and counting active rows for that kind inside the same transaction as the new account row — never a coarser subsystem-wide lock. Only `seats.release` (reserved, SYSTEM-only) ends a reservation; `restoreAccount` (same capability) is the sole path back from `RELEASED`, re-reserving a seat and issuing a fresh one-time credential for the *same* account identity, since nothing in the requirements distinguishes "restore" from "recreate" and the account/audit trail is more useful preserved. Ordinary deactivate/reactivate (staff) and block/unblock (parent) explicitly refuse a `RELEASED` target so a delegated admin without `seats.release` cannot silently reinstate login access outside the seat ledger.

The only structural inter-module dependency implemented is FINANCE's re-enable-after-disable catch-up gate (`POST /modules/:key/preview` then `catchupAcknowledged: true`); no other dependency between FINANCE/ATTENDANCE/EXAMS/HOMEWORK/HEALTH is stated in ACCESS_AND_LICENSING.md, so none is fabricated. The catch-up preview honestly reports zero missing periods pending Phase 14's billing engine; `moduleChangeImpacts` is the named integration point for that phase. `module_settings` has no branch column — "identical across every branch" holds by construction, not by a runtime check.

Nursery brand/theme (`branding.manage`) stays reserved (SYSTEM-only), matching the settings-ownership table exactly; there is no delegable branding capability. Contrast validation runs the same WCAG formula (`packages/domain`) on both server (blocking save) and client (live preview) using the exact worked examples in UX_AND_BRANDING.md. `GET /api/v1/licensing/branding` is the one public, pre-authentication API surface added this phase, deliberately isolated behind its own `AuthClient` instance from the authenticated app (see LICENSING_AND_SETTINGS.md's verification notes for why). See [LICENSING_AND_SETTINGS.md](LICENSING_AND_SETTINGS.md) for services, route contracts, capability catalog additions, migration `0003_licensing_settings.sql`, and detailed evidence.

### 2026-09-13 — Phase 04 scope and delegation defaults (D30)

R02/R03/R05/U02: scope mode is explicit account data (`BRANCH` or `CLASSROOM`), independent of editable role names. Existing staff default to CLASSROOM with no assignments. Capabilities union across roles; classroom restrictions never disappear merely because a second role is attached. SYSTEM controls role definitions, per-account delegated assignable role IDs, and the separate sensitive-financial-edit entitlement. Reserved capabilities cannot be attached to editable roles.

Delegated staff administrators require BRANCH scope and authority over every existing/requested target branch. Both existing and requested roles must be explicitly delegated and their capabilities must remain a subset of the actor's capabilities. Staff cannot edit themselves, unassigned accounts, partly inaccessible accounts, or sensitive-entitled accounts. SYSTEM performs initial scope assignment. General account creation remains Phase 05/06 and must reserve slots through its domain service; this phase adds no provisioning shortcut.

Authorized branch creation assigns only the newly created branch to its creator. Staff may add age-group options; SYSTEM alone edits existing shared age groups because such edits affect all branches. Classroom branch identity stays immutable; staff assignment moves preserve original audit ownership. Capacity is advisory and no child occupancy is fabricated before Phase 06. Strict version checks protect mutable records/assignments. Transactional policy locks and a global revision invalidate current access, with five-second in-memory UI revalidation and immediate server checks. See ORGANIZATION_AND_POLICY.md for services, route contracts, permission fixtures, and migration `0002_organization_policy.sql`. No later-phase financial or guardian actions are enabled by the capability catalog.

### 2026-09-13 — Phase 03 authentication defaults (D29)

R02/U03: normalize usernames with NFKC, trim outer whitespace, and locale-independent lowercase; accept 3–64 Unicode letters/numbers or `.`, `_`, `-` without internal whitespace. Passwords are 15–128 characters without trimming or composition rules. Use Node scrypt (N=131072, r=8, p=1, random 16-byte salt, 64-byte key), following the [OWASP password storage guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).

Sessions have a 12-hour absolute limit and 30-minute sliding idle limit. Explicit rotation invalidates the prior token without extending the absolute limit; password changes issue a new session and revoke every previous session. Temporary credentials expire after 24 hours, can sign in once, and create a restricted 15-minute setup session. An abandoned setup requires another Superadmin reset (or local SYSTEM recovery). Login is limited to 10 attempts per normalized identity and 30 per direct peer IP per 15 minutes, shared in PostgreSQL. Password/reset attempts use the same limiter by actor ID. Proxy headers are untrusted until narrowly configured in the deployment phase.

Bootstrap is single-use under a transaction lock and persistent marker; SYSTEM recovery updates the existing reserved account, never creates another. Both local commands consume bounded JSON through private stdin and never print credentials. Assisted reset requires the reserved SYSTEM identity and its current password, returns a random temporary password once, and does not activate or unblock the target. Public account messages are shown only after valid credentials or an existing session; internal status reasons are never public. General provisioning, block UI, roles, slots, and license policy remain their planned phases. Migration: `0001_authentication.sql`; API namespace: `/api/v1/auth`; current-account responses explicitly report `policyReady: false` and no unimplemented business capabilities.

Append a dated decision with reason, affected requirement IDs, migrations/API impact, and affected phase files. Update canonical rules and acceptance fixtures together. Never silently replace an equal split with a proportional split, revive removed complaints/media, or turn manual blocking into automatic debt enforcement.

### 2026-09-13 — Phase 06 child, guardian, and document defaults (D32)

R05/U08, D07/D19/D20: onboarding requires child code/name/birth date/branch and guardian profile name/mobile with per-child relationship and independent read/finance/pickup/notify flags. Classroom is explicitly nullable, matching unassigned admissions; such children never qualify for daily classroom operations. Codes are stable installation-local identifiers, normalized uppercase; duplicate conflicts are generic and never disclose foreign families. Existing parents reuse their account and reservation. Only SYSTEM can initialize a standalone Phase 05 parent profile without an existing accessible family link. New account credentials come from the existing quota service, never caller passwords. Actor-scoped operation UUIDs make retries atomic and return no original credentials on replay. New onboarding requires a configured, usable license even for SYSTEM.

ACTIVE may transition to PAUSED or ARCHIVED; PAUSED may resume or archive. ARCHIVED is final in V1 (no restoration or deletion action specified). Lifecycle changes take effect on the current Cairo date, require a reason, preserve history and all seat reservations, and never alter existing fee agreements. Paused guardian cards expose only name/contact message; active sibling views remain available. Archive emits a durable integration event for Phase 14 to end future monthly generation, retaining existing obligations. Cross-branch transfer is rejected until Phase 17; same-branch classroom history is retained. Classroom capacity is advisory.

Generic administrative documents are staff-only under documents.manage plus current child scope, even if a guardian has read permission. Accept PDF/JPEG/PNG up to 5 MiB before and after actual parsing/re-encoding; images are limited to 16 million pixels, PDFs to 100 pages, encrypted/interactive PDFs rejected. Names/optional expiry are metadata, never file paths or automatic deletion. Generated UUID blobs live beneath PRIVATE_FILES_DIR/child-documents, outside the web application, with attachment-only authenticated downloads. Retirement removes availability while retaining historic bytes. SYSTEM support cleanup removes only unreferenced generated files older than 24 hours; failed uploads reconcile committed references before deleting candidates.

Prerequisite tightening: parent block/unblock now checks all active linked-child scopes under a policy lock; unattached parents are SYSTEM-only. Migration 0004 also enforces seat category matches account kind and immutable reservation ownership, closing a missing ledger constraint without changing reservation release rules. New capabilities are delegable data (children.read, children.manage, guardians.manage, documents.manage), not silently added to existing roles. See [CHILDREN_AND_DOCUMENTS.md](CHILDREN_AND_DOCUMENTS.md) for routes, locks, migration and verification. Phase 06 scope only; finance/transport steps remain explicitly unavailable until implemented.

### 2026-09-14 — Phase 07 health, pickup, and incident defaults (D33)

R03/R08/R09/U19/U20, D19/D26: authorized pickup and incidents become real optional modules (`PICKUP`, `INCIDENTS` in `module_settings`, inserted enabled) alongside `HEALTH`, because R03 lists them as optional and A31 requires disable behavior; module writes return the distinct code `MODULE_DISABLED`, reads for authorized staff keep history, and the HEALTH emergency view stays readable while disabled. Six delegable capabilities (`health.read/manage`, `pickup.record/manage`, `incidents.read/manage`) are data assigned through Phase 04 roles; guardians act only through their own link flags (`read` to view, `pickup` to manage authorized people, `notify` as event recipients).

Health is one bounded entry shape (note, allergy, alert, emergency contact with mobile) with critical/info severity and retire-not-delete; nothing about medication or dosing exists. Authorized people carry name/phone/relationship and a date range (one day = same from/until). Management restrictions are PROHIBITED_COLLECTOR (matched by normalized name or phone) and REVIEW_REQUIRED (every authorized person needs an approval later than the restriction); private notes are visible only to `pickup.manage`, summaries to `pickup.record`, and guardians see only a neutral "awaiting nursery confirmation" flag. A release needs a currently permitted collector (authorized person or pickup-permitted guardian), `callConfirmed: true`, and a pickup-permitted linked guardian who was called; the record stores the Cairo business date and snapshots, is append-only, and has no arrival/departure clock fields. Incident description/occurrence are immutable after creation; follow-up fields are versioned. Each report/update commits an append-only `notification_events` row with a recipient snapshot and hint payload for Phase 12, which must revalidate links at dispatch. WhatsApp numbers are normalized server-side (digits only, Egyptian default country code 20) and rendered as user-initiated `wa.me` links; nothing is sent automatically. Test-fixture-only change: the disposable auth fixture destroys lingering keep-alive sockets before `app.close()`. See [SAFETY.md](SAFETY.md) for routes, rules, migration `0005_safety.sql` and verification.
