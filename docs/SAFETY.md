## Permissions (safety)

Six delegable capabilities are data in migration 0005, never role names: `health.read` (staff emergency view), `health.manage` (create/update/retire health entries), `pickup.record` (view pickup section, record releases), `pickup.manage` (add/deactivate authorizations on behalf of families, review authorizations, record/end restrictions and prohibited collectors, see private notes), `incidents.read`, `incidents.manage` (report/follow up). `*.manage` implies the matching view. Every staff action also requires the child's branch/classroom scope through `requireChild`; SYSTEM holds all capabilities. Guardian access uses only the guardian's own active link: `read` for the guardian safety view (health entries, incidents), `pickup` to list/add/remove authorized people, `notify` to be a notification recipient. Neither path falls back to the other; guessed or foreign IDs fail closed with FORBIDDEN.

Module flags (`module_settings` HEALTH, PICKUP, INCIDENTS; PICKUP/INCIDENTS added by 0005 per R03) gate every write with the distinct code `MODULE_DISABLED` (`safety.moduleDisabled`, 403). Reads for authorized staff remain available while disabled, including the D26 emergency view; guardian sections become `null` and the parent panel hides them.

## Routes

Staff: `GET /api/v1/children/:id/safety` → `ChildSafetyView` {modules, child-scoped capabilities, child, guardians (name, relationship, mobile, normalized `whatsappNumber`, link permissions), health (all entries, retired last) | null, pickup {authorizations with `blockers`, restrictions (`privateNote` only with pickup.manage), last 100 records} | null, incidents | null}. Sections are `null` without the capability. `POST /children/:id/health-entries`, `PUT /health-entries/:id`, `POST /health-entries/:id/retire`; `POST /children/:id/pickup-authorizations` (guardian with pickup or staff pickup.manage), `POST /pickup-authorizations/:id/deactivate` (same actors), `POST /pickup-authorizations/:id/review` {expectedVersion, decision APPROVED|REJECTED, note}; `POST /children/:id/pickup-restrictions` {kind PROHIBITED_COLLECTOR (name required, optional mobile) | REVIEW_REQUIRED, summary, privateNote}, `POST /pickup-restrictions/:id/deactivate`; `POST /children/:id/pickup-records`; `POST /children/:id/incidents` and `PUT /incidents/:id` (32 KiB body limit for bilingual narratives). Guardian: `GET /api/v1/parent/children/:id/safety` → `GuardianSafetyView` {modules, permissions, health | null, pickup {authorizations with `pendingNurseryConfirmation`} | null, incidents | null}. Mutable rows use strict `expectedVersion` (STALE_VERSION on conflict); all payloads are strict schemas in `packages/contracts/src/safety.ts`.

## Health notes, alerts, emergency contacts

`health_entries` holds kinds NOTE, ALLERGY, ALERT, EMERGENCY_CONTACT with title, body (≤1000), severity INFO|CRITICAL, optional mobile (required exactly for EMERGENCY_CONTACT, database-checked). No medication, dose or schedule fields exist (U19). Retirement keeps the row (`active=false`) and its audit; guardians see active entries only, staff see history. Ordering: active, CRITICAL first, then allergy/alert/contact/note. Edits are rejected for ARCHIVED children and whenever HEALTH is disabled; the staff emergency view (`health.read`) still returns guardian contacts and entries while disabled (D26/A31).

## Pickup rules

Authorized people: name, mobile, relationship, `validFrom`, nullable `validUntil` (≥ from); one-day authorization is `validFrom = validUntil`. Guardians with link `pickup` and staff with `pickup.manage` may add/deactivate; the child must be ACTIVE. Management records `pickup_restrictions`: PROHIBITED_COLLECTOR matches an authorization by NFKC/case/space-normalized name or by normalized phone (same normalizer as WhatsApp); REVIEW_REQUIRED demands an APPROVED review whose `reviewed_at` is later than the restriction's `created_at`, so a newer restriction re-blocks older approvals until management reviews again. Restriction `summary` is visible to `pickup.record` staff; `privateNote` only to `pickup.manage`; guardians never see restrictions, review state or blocker names — only `pendingNurseryConfirmation` (true for PROHIBITED_COLLECTOR or REVIEW_REQUIRED).

Release recording (`pickup.record`, PICKUP enabled, child ACTIVE — otherwise `safety.childNotActive`): collector is `{kind: AUTHORIZED_PERSON, authorizationId}` or `{kind: GUARDIAN, accountId}`. Computed blockers INACTIVE, REJECTED, NOT_YET_VALID, EXPIRED reject with `safety.collectorNotPermitted`; PROHIBITED_COLLECTOR → `safety.prohibitedCollector`; REVIEW_REQUIRED → `safety.unresolvedRestriction`; a guardian collector needs an active link with `pickup`. `callConfirmed` must be true (`safety.callNotConfirmed`) and `calledGuardianId` must be an active linked guardian with `pickup` (`safety.calledGuardianNotPermitted`). All rule rejections are 409 VALIDATION_ERROR with those message keys. The record stores the current Cairo business date, collector snapshots, called guardian, `call_confirmed` (checked true) and optional note; `pickup_records` is append-only by trigger and has no arrival/departure clock columns (`created_at` is private audit metadata, never returned). Every action writes `child_audit_events` (`pickup.recorded`, `pickup.authorization_*`, `pickup.restriction_*`). The application records the procedure; it cannot verify a caller physically.

## Incident event contract

`incidents`: `occurredOn` (date, not future), `occurredTime` (HH:MM wall clock, Cairo), description and actionTaken (1–2000), `guardianInformed` with `contactMethod` CALL|WHATSAPP|IN_PERSON|IN_APP (database-checked: informed ⇔ method present), optional followUp, status OPEN|CLOSED, version. Description and occurrence are immutable after creation; `PUT` updates action/informed/method/follow-up/status with `expectedVersion` and audits before/after. Reporting requires `incidents.manage`, INCIDENTS enabled and an ACTIVE child; the classroom is snapshotted.

Every report and update inserts one row into append-only `notification_events`: `id`, `kind` (`incident.reported` | `incident.updated`), `child_id`, `branch_id`, `resource_type='incident'`, `resource_id`, `resource_revision` (incident version), `recipient_ids` (active links with `notify` at creation; Phase 12 must revalidate links at dispatch), `payload` {childId, incidentId, occurredOn} as an invalidation hint only (never the description), `created_at`. Events commit in the incident transaction, so the record is preserved when no live delivery exists; dispatch state belongs to Phase 12 tables, not to this immutable log. Guardians with `read` see committed incidents in their safety view.

## WhatsApp links

`normalizeWhatsAppNumber` (packages/domain) returns digits only: `+`/`00` international prefixes are kept, Egyptian local numbers starting with 0 get country code 20, 8–15 digits required, otherwise `null`. The server returns `whatsappNumber` per linked guardian; the client builds `https://wa.me/<digits>` through `whatsAppLink`, rendered as a user-initiated `target=_blank` `rel=noopener noreferrer` link in the staff emergency view. The application never sends WhatsApp, SMS, email or push messages; guardian views contain no `wa.me` links.
