## Delivered behavior and contracts

Subjects and exam types are simple editable/retirable nursery-wide catalogs (`subjects`, `exam_types`; id/name/enabled/version), gated by a new delegable `exams.catalog` capability separate from `learning.publish`. Exam definitions (`exams`: name, subject, type, classroom, `assessedOn`, `gradeFormat` NUMERIC/LABEL, maximum/decimal-allowed or label options, creator) are created by classroom-scoped staff with `learning.publish` and are append-only afterward — this phase has no exam-metadata edit endpoint. Every exam snapshots the subject/type name it used at creation, so a later catalog rename never rewrites a historical exam's display.

Results are entered per exam on that exam's own classroom roster: outcome `RESULT` (exactly one of a numeric score, exact to two decimals and bounded by the exam's own snapshotted maximum/decimal-allowed flag, or a label from the exam's own snapshotted label list) or `CHILD_ABSENT` (no score/label). A missing result is distinct from zero everywhere (roster, history, underlying learning event). Corrections append a new event with a required reason; the original stays queryable. `No exam today` publishes N/A for a wholly untouched classroom/date roster and is refused once any exam already exists for that classroom/date.

Because a classroom can have several exams the same day, all of a child's exam activity that day shares **one** EXAM checkpoint slot/revision chain (the existing Phase 08 daily-progress-bar slot), while each individual exam's own outcome/score/label/comment lives in adapter-owned `exam_results`, keyed by its own learning event. The shared slot's status is recomputed on every exam-result write from every exam scheduled that classroom/date: pending while any applicable exam lacks an outcome, N/A only if every applicable exam resolved child-absent, otherwise resolved. Creating a new exam for a classroom/date that already looked resolved reopens every affected child's slot back to pending (bounded to the same ≤100-child roster page) via an appended transition. This required a narrow, deliberate extension to the Phase 08 built-in adapter contract: `LearningService.appendInTransaction` accepts `{ aggregateTransition: true }`, usable only for `kind==='EXAM'`, letting a transition land on an unchanged status without touching the public custom-checkpoint transition rule (changed status, unchanged note) that every other kind still enforces.

Child exam history (`GET /api/v1/exams/children/:id/history`) lists exams applicable to a child (classroom matched date-effectively via `child_classroom_history`, independent of whether a daily snapshot was ever created for that date) with subject/type/date filters, showing each exam's current result or explicit missing state and whether it was corrected. Numeric and label results are never averaged or converted into each other.

API paths are under `/api/v1/exams`: `catalog` (get/save subjects and types), root (create, list by classroom/date, detail), `:id/roster`, `results` (batch publish), `results/corrections`, `no-exam-day`, `children/:id/history`. The teacher UI is `/teacher/exams`; guardian child detail includes a filterable exam history panel. Copy is English and Egyptian Arabic. D36, EXAMS.md, DAILY_LEARNING.md, and API_AND_DATA_CONTRACTS.md record the decisions/contracts.
