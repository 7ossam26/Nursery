Payments validate actual account method, original expense branch, effective date, recorded funds and current actor authority.

Expense payment locks settings, actor operation, expense and accounts; configuration takes settings before the operation to avoid inversion. Source, signed outflow, audit and durable retry result commit together. Transfer requires branch-level `treasury.manage` over both accounts, actual funding and equal opposite source/destination movements; source/leg uniqueness and deferred PostgreSQL constraints reject incomplete or mismatched postings. Both-side history permission prevents exposing an inaccessible destination. Transfers never enter expense paid totals.

`/api/v1/expenses`: options, list, create, categories, settings, `:id/{approve,cancel,pay,history,documents}`. `/api/v1/finance/transfers`: paired posting and scoped history. Lists/totals share the same branch/classroom/state predicate and are paginated. History uses business dates and source reasons/actors, omitting private audit timestamps.

`PrivateDocumentStore` extracted from existing child-document filesystem handling; the child service and expense service reuse identical root/symlink/key/integrity guards and the existing PDF/JPEG/PNG parser/re-encoder. Expense uploads additionally use actor operation identity; file bytes are hashed for that identity and omitted from audit JSON. Current finance/document capability, original expense scope and enabled Finance are checked on every list/download. Attachment is private/no-store; no storage paths or keys are exposed. Retirement retains referenced historical bytes. Failed transaction candidates are removed only after checking no DB reference; uncertain DB acknowledgement preserves candidates for conservative SYSTEM cleanup of old unreferenced validated UUID files.

Pages `/administration/{expenses,transfers}` provide bilingual cash-effect explanations, explicit actual account/payment confirmation, full filtered pending/paid totals, categories/threshold controls, history/documents and FinancialCore status lookup before identical uncertain retry. Shared controls and scoped reads reused. No browser automation or persisted offline mutation queue.

## Corrections, credits, and refunds

Migration0016 and `CorrectionService` add immutable source-specific corrections for PAYMENT receipts, settled expenses, internal transfers, and tuition installments. Receipt/expense/transfer correction reverses the full original effect on the current Cairo business date and may append a replacement. Original source rows, dates, branch/account attribution and reasons remain unchanged. Receipt allocation reversals and replacement allocations drive the existing installment projection; expense states expose REVERSED/CORRECTED with the canonical replacement outflow; all transfer correction legs still net to zero. An already corrected receipt or one whose allocations were reclassified into tuition credit is not silently unwound again.

Tuition reduction appends a negative obligation adjustment. Unpaid remaining value is reduced first; settled excess deterministically restores newest applied credits, then reverses newest actual receipt allocations. Actual paid excess becomes a noncash credit whose `credit_origins` identify each immutable original receipt/account. Existing explicit credit receipts are backfilled and new credit receipts write the same origin contract. Applying credit remains cash-neutral.

Refunds lock the child, credit, origin and sorted treasury accounts; enforce both aggregate `credit_balances.remaining` and origin availability; preserve the original receipt/account; and post exactly one negative REFUND movement from the original or an explicitly confirmed, scoped, funded alternative account. Application/refund races cannot make either balance negative. All mutations require `finance.correct`, explicit sensitive entitlement (including SYSTEM), source/replacement scope, reason, module availability, and FinancialCore operation/audit identity. Replays recheck entitlement and stored resources. Cash writers reuse account locks, recorded-funds validation and the counted-date SQL guard. Deferred validators reject incomplete sources, excess signed allocation reversals, mismatched correction legs, credit origins and refund movements.

`/administration/corrections` provides bilingual receipt/expense/transfer reversal/replacement, tuition reduction and refund forms, source/account warnings, explicit confirmations, immutable correction/refund history and the shared uncertain-operation status flow. The UI uses current-date corrections; refund API business dates remain explicit and cannot pass an active counted date.
